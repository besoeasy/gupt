# AGENTS.md

The rules for changing this repository: how it looks, how it stores data, and what may never break for a client that is already installed. Every item names the file that owns the rule, and the test or script that fails when it is broken — when the code and a rule here disagree, fix both in the same commit. Read the item that touches your change before you start; the ones about storage and the support window are not negotiable.

1. **Write CSS by hand.** No Tailwind utilities. When you touch a component that still uses them, replace them with semantic classes and keep the rules in that component's scoped `<style>` block; add to `src/index.css` only when a rule is genuinely global (theme tokens, shared transitions, resets).
2. **Write every rule unlayered.** There is no Tailwind alias layer and no `@layer gupt-components`; all component CSS is hand-written and competes with `src/index.css` on specificity alone. Do not reintroduce a layer wrapper to win a cascade fight — raise the selector's specificity or move the shared rule into `index.css` instead.
3. **Style both themes through tokens.** Every screen, light and dark: use the `--app-*` tokens (or `color-mix` with them) instead of hardcoded colors, and check the screen with the theme switched both ways. A translucent tint repeated in more than one component becomes an `--app-*` token in `src/index.css` — the opaque surface as its fallback, redefined as `color-mix` in the shared `@supports (color: color-mix(in lab, red, red))` block, never a palette `color-mix` written per component. The existing ones are `--app-border-quiet`/`--app-border-faint`, `--app-surface-tint`/`--app-surface-tint-soft`, `--app-surface-inset`/`--app-surface-inset-strong` and `--app-surface-raised-tint`/`--app-surface-raised-tint-soft`; they need no `[data-theme="light"]` override because they are built from `--app-surface-raised`, `--app-surface` and `--app-bg-soft`, which each theme already supplies.
4. **Fix light mode where the class lives.** A `[data-theme="light"] .block__element { … }` block goes in the component that owns the class, right after the rule it corrects, overriding only the declarations the dark palette gets wrong (usually `color`, `background-color`, `border-color`). Only overrides several components share — relay tier badges, Rabta status, the navbar header — belong in `index.css`.
5. **Mobile-first, animated, never hover-only.** No horizontal scroll, touch targets of at least 44px, no interaction that only works on hover, a fade-in on load, and hover/touch feedback on every interactive element.
6. **No back buttons where the navbar shows.** A route that renders the navbar gets no back element; add one only on routes that hide it.
7. **Split components early.** PascalCase, one per file, in `components/`. Split when a file passes ~500 lines, when markup or logic repeats, or when a block has its own state. Props instead of copy-pasted variants, complex logic in composables or helpers, and no splitting of simple one-off markup — extracted components keep every design rule above.
8. **Draw our own SVG.** Hand-written logos and marks only: no logo packages, stock art, CDN or hotlinked images. Reuse the G-mark geometry from `public/favicon.svg` (and the inline mark in `WelcomeView.vue`) instead of redrawing it. Shareable files live in `public/`; small UI marks are inlined with `currentColor` so they follow the theme. Standalone files get `role="img"` plus `<title>`/aria-label, decorative inline copies get `aria-hidden="true"`, and nothing references an external font or image.
9. **Generate avatars locally, and freeze the algorithm.** `src/lib/avatar.js` hashes the seed into a mirrored 5×5 grid and returns a `data:image/svg+xml` URI — no dependency, no request, because the seed is a public key and fetching a face from anywhere would hand a third party the contact graph. A changed grid, bit order or palette repaints every face in every address book, so treat it like a protocol version, not styling: `test/avatars.test.js` pins the output with digests and regenerating them is a release decision. Keep each URI to a few hundred bytes.
10. **Treat the IndexedDB cache as disposable.** Relays are the source of truth. The database name is derived from `STORE_SPECS` (`schemaFingerprintOf`), so never hardcode `gupt_cache_*` names or read `STORE_SPECS` from app code — the layout belongs to `src/lib/idb.js` and `test/schema-name.test.js` guards the derivation. Never write a migration, `DB_VERSION` or upgrade reconciliation code: change the layout and the next load opens a fresh database, then sweeps the old one. Unsent self-authored events live in the `gupt_outbox_v1` localStorage queue, never in IndexedDB only.
11. **Ship one version, and let it be the release date.** `package.json` `version` is the UTC release date and nothing else, `YYYY.M.D` — `2026.11.20`, `2026.1.5`. Month and day are unpadded because semver forbids leading zeroes (`semver.valid("2026.11.05")` is `null`, and `npm version` rewrites the padded form to `2026.11.5`). One release per day, no counter. `npm run release:bump` writes that date into `package.json`, `package-lock.json` and the flatpak metainfo, and `npm run release:check` is the gate; never hand-edit any of the three. Everything else reads it: the git tag and GHCR image tag, the flatpak bundle name, the AppStream `<release>` entry and the `w` writer stamp. The app itself never renders the version — Settings shows `__APP_BUILD_TIME__`, and `__APP_VERSION__` exists only to feed that stamp.
12. **Honour the 400-day support window.** Every build must keep working for a client built at any point in the last 400 days, and every client must keep working against a relay up to 400 days old. The numbers live in `src/config/compat.js` — `RETENTION_DAYS` (366), `COMPAT_MIN_SLACK_DAYS` (30), the derived `MIN_SUPPORTED_DAYS` (396) and `COMPAT_WINDOW_DAYS` (400) — and nowhere else; `test/compat.test.js` fails if the window drops below retention plus slack, or if the README stops stating the live numbers. The window covers the sign-in path, not the remembered device: `VAULT_TTL_MAX_MS` stays at 3 days, so returning after months means the secret phrase and PIN, and that path must keep working with any secret generated inside the window.
13. **Keep protocol versions off the calendar.** `RABTA_VERSION`, the vault record `v` and the ciphertext envelope stay independent integers. Never let them follow the calendar or the app version — the 400-day promise is about those numbers, not the release label.
14. **Know what is breaking.** Needing the whole window: the event envelope (ciphertext `v1`/`v`, `RABTA_VERSION`, sealed payload fields, blob part format), event `type` and tags, the secret+PIN key and address derivation, the `gupt_vault_v1` record shape (`v`), `gupt_outbox_v1` entries, localStorage keys, and the relay `api_version`. Not breaking: the `gupt_cache_*` IndexedDB, which is disposable and refetched. Additive changes need no shim, but readers must skip what they do not know — a new event `type`, an unknown payload field, a newer ciphertext `v` — instead of throwing.
15. **Deprecate in three steps.** Read both formats while writing the new one, note it in the release notes, then drop the old read path once `COMPAT_WINDOW_DAYS` has passed since the last build that wrote it.
16. **Date every shim.** Every shim is a migration with an expiry date — no permanent shims, no "keep for safety", no undated TODO. Tag the old path in the same commit that introduces it: `// COMPAT: remove after YYYY-MM-DD — <old format + why it exists>`, with the date set to the last build that wrote the old format plus `COMPAT_WINDOW_DAYS` (400 days).
17. **Delete expired migrations first, on every release.** Run `grep -rn "COMPAT: remove after" src` before cutting a release; for every tag dated today or earlier, delete the old branch and its tag in that release. Do not extend the date. If the old format is still in the wild, that is a new 400-day window with a new date and its own release-note entry, not an excuse to keep the old path. `npm run release:check` fails on an expired tag (`expiredShims()` in `scripts/release.mjs`), so the release cannot be cut around it — and this is the deadline that is easiest to forget, so run the grep even when the gate is green.
18. **Stamp what you write.** `src/lib/writerVersion.js` stamps `w` (the release) onto vault records in `save()` and onto all event `data` in `finalizeEvent` — the single choke point covering DMs, groups, feed, passwords, notes, bookmarks, invites, profiles and receipts; new stored shapes go through those same two paths, never a second stamp. `w` is metadata, never a readability gate: readers accept or reject on the protocol integers and use `isWrittenBefore()` only to choose a migration path, each of which still needs its own dated tag. The stamp is coarse by design — release only, never a commit hash or timestamp — because it sits plaintext on relays next to already-plaintext nonces and labels.
19. **Repair on read, never in the background.** An older item is moved to the current version the moment a reader detects it: detection is `isWrittenBefore(item, WRITER_VERSION)` (a missing `w` counts as old) and the repair is a rewrite through the same write path that owns the item, in the same read, before the value is returned — copy `keyVault.open()`, `readOutboxBox()` or `loadPersisted()` in `stores/settings.js`. Never park an old shape for a batch job, a background sweep or "a future release": if a reader can see it, that reader upgrades it. Repair scope is everything this device owns (vault records, the outbox, localStorage settings and queues, cache rows); signed relay events are immutable, so a self-authored event is re-published in the current shape at its next write and everyone else's stays read-only until retention expires. Repair does not replace the dated tag: the tag covers what this build cannot repair.
20. **Never rename a storage key.** Key-versioned names (`…:v1`) are not a substitute for a payload header — renaming the key to add a field throws the user's data away. Keep the key stable and version the payload with `v` + `w` (`src/lib/storedMap.js` for map-shaped stores). Backfilling a missing field next to the existing write (`record.x = record.x ?? …`) is not a migration and needs no tag; changing what a field means is. GUPT has not shipped its first release yet, so never write a shim for a pre-deploy shape — the first deployment starts both clocks, the 400-day window and read-repair.
